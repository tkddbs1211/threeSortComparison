# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 실험 환경 및 방법
- 데이터: 1 ~ 100,000 범위의 무작위 정수 (중복 허용)
- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 각 데이터 크기마다 원본 배열을 하나 생성하고, 모든 알고리즘은 이 원본의 복사본을 정렬함
- 정렬 후 `is_sorted()` 함수로 오름차순 정렬 여부를 검증함
- 실행시간은 `clock()`으로 정렬 함수 호출 직전 ~ 직후만 측정함 (데이터 생성, 배열 복사, 출력 시간 제외), 단위는 ms

## 3. 분석

### 3-1. 데이터 크기 증가에 따른 비교 횟수 변화
세 알고리즘 모두 n이 2배가 될 때 비교 횟수가 약 2.1 ~ 2.2배 증가했다. 2배보다 조금 더 늘어나는 것은 log n 항 때문이며, 세 알고리즘 모두 O(n log n)으로 증가함을 확인할 수 있다.

n = 20,000일 때 n·log₂n ≈ 285,754를 기준으로 보면 다음과 같다.
- 병합 정렬: 약 0.91·n log n → 가장 적음
- 퀵 정렬: 약 1.15 ~ 1.2·n log n
- 힙 정렬: 약 1.79·n log n → 가장 많음

**힙 정렬이 가장 많은 이유**: 힙 속성을 복구(sift down)할 때 한 레벨 내려갈 때마다 ① 왼쪽/오른쪽 자식 중 큰 값 선택, ② 부모와 큰 자식 비교로 최대 2번 비교한다. 또한 정렬 단계에서 루트로 올라오는 값은 힙의 마지막 원소(작은 값)이므로 거의 항상 리프까지 내려가야 한다. 따라서 약 2n log n에 가까운 비교가 발생한다.

**병합 정렬이 가장 적은 이유**: 이미 정렬된 두 부분 배열을 합칠 때 원소 하나를 내보낼 때마다 비교가 최대 1번이며, 한쪽이 먼저 소진되면 나머지는 비교 없이 복사된다. 분할이 항상 정확히 반으로 이루어져 깊이가 log n으로 고정된다.

**퀵 정렬**: 분할 시 각 원소를 피벗과 1번씩 비교하지만, 피벗이 항상 중앙값이 되지는 않아 분할이 불균형해지는 경우가 생기므로 병합 정렬보다 비교 횟수가 많다. (이론적 평균 ≈ 1.39·n log n)

### 3-2. 실행시간 차이
실행시간은 대체로 **퀵 정렬 < 병합 정렬 ≈ 힙 정렬** 순서였다.

- **퀵 정렬**은 비교 횟수가 병합 정렬보다 많은데도 가장 빨랐다. 추가 배열 없이 제자리에서 교환하고, 인접한 원소를 순차적으로 접근하므로 캐시 효율이 좋기 때문이다.
- **병합 정렬**은 비교 횟수가 가장 적지만, 병합할 때마다 임시 배열로 복사하고 다시 원본 배열로 되돌리는 데이터 이동 비용이 커서 퀵 정렬보다 느렸다.
- **힙 정렬**은 비교 횟수가 가장 많고, 부모(i)와 자식(2i+1, 2i+2) 사이를 오가며 멀리 떨어진 메모리에 접근하므로 캐시 효율이 낮아 느린 편이었다.
- n이 작을 때(1,000 ~ 2,000)는 실행시간이 0.1 ~ 0.3ms로 매우 짧아서, `clock()`의 해상도와 측정 오차 때문에 순서가 뒤바뀌는 경우도 있었다.

### 3-3. 메모리 사용량 차이
- **힙 정렬 (84 Bytes, 일정)**: 입력 배열 자체를 힙으로 사용하고 sift down을 반복문으로 구현해 재귀가 없다. 그래서 n과 상관없이 보조 변수와 함수 호출 2단계만 사용한다. → O(1)
- **병합 정렬 (n×4 + α)**: 크기 n의 임시 배열이 필요하므로 n에 비례해 증가한다 (20,000개일 때 80,512 Bytes). → O(n)
- **퀵 정렬 (약 600 ~ 1,100 Bytes)**: 별도 배열은 없고 재귀 호출 스택만 사용한다. 최대 재귀 깊이가 log n에 비례하므로 느리게 증가한다. → 평균 O(log n)

### 3-4. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이
- 무작위 데이터에서는 세 피벗 방법의 비교 횟수 차이가 크지 않았다 (n = 20,000에서 약 4% 이내). 데이터가 이미 무작위이므로 첫 번째 원소를 피벗으로 골라도 무작위 피벗과 같은 효과가 나기 때문이다.
- **Median-of-Three**는 대부분의 크기에서 비교 횟수와 재귀 깊이(메모리)가 가장 작았다. 세 값의 중앙값을 피벗으로 쓰면 분할이 더 균형 있게 이루어지기 때문이다. 피벗 선택에 2 ~ 3번의 비교가 추가되지만, 분할이 균형 잡혀서 얻는 이득이 더 크다.
- **Random**은 `rand()` 호출 비용 때문에 실행시간이 약간 더 길게 나왔다.
- 만약 데이터가 이미 정렬되어 있다면 First 방식은 매번 최솟값을 피벗으로 골라 O(n²)과 재귀 깊이 n이 되지만, Random과 Median3는 이런 최악의 경우를 피할 수 있다.

## 4. 시간 복잡도 및 공간 복잡도 비교

| 알고리즘 | 최선 | 평균 | 최악 | 추가 공간 | 안정성 |
|---|---|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(n log n) | O(1) | 불안정 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | O(n) | 안정 |
| 퀵 정렬 | O(n log n) | O(n log n) | O(n²) | O(log n) ~ O(n) | 불안정 |

- 힙 정렬은 최악의 경우에도 O(n log n)이고 추가 메모리가 거의 없지만, 비교 횟수가 많고 캐시 효율이 낮다.
- 병합 정렬은 비교 횟수가 가장 적고 항상 O(n log n)이지만, O(n)의 추가 메모리가 필요하다.
- 퀵 정렬은 평균적으로 가장 빠르지만, 피벗 선택에 따라 최악의 경우 O(n²)이 될 수 있다.

## 5. 메모리 사용량 측정 방법 및 계산 기준
프로파일링 도구 대신 **직접 계산** 방식을 사용했다. 원본 데이터 배열은 공통 비용이므로 제외했다.

- 재귀 호출 1회당 스택 프레임 크기를 **32 Bytes**로 가정했다 (`FRAME_SIZE`, 이전 과제와 동일한 기준).
- 각 재귀 함수에 들어갈 때 `current_recursion_depth`를 증가시키고, 그 최댓값을 `max_recursion_depth`에 기록해서 실제 최대 재귀 깊이를 측정했다.

| 알고리즘 | 계산식 |
|---|---|
| 힙 정렬 | 보조 변수 int 5개(i, temp, parent, child, temp) × 4 + 호출 스택 2단계(heap_sort → sift_down) × 32 = **84 Bytes** |
| 병합 정렬 | 임시 배열 n × sizeof(int) + 최대 재귀 깊이 × 32 |
| 퀵 정렬 | 최대 재귀 깊이 × 32 (보조 배열 없음) |
